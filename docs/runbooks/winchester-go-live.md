Составлено 01.11.2026 по ветке `audit/winchester-handoff-2026-10-31`; PR №2 слит в `dev` 01.11 (`158e36e`). Кому: владельцу — что

«проверено», проверено на локальной копии и заглушках (раздел 1). Приёмка по сценариям — `docs/runbooks/winchester-acceptance.md`,
инструкция для Кайрата — `docs/winchester-kairat-handoff.md`.

## 0. Коротко

- **Что выкладываем:** ветку `dev` вместе с PR №2 (аудит, ревью, повторы Green-API) — в `main`, то есть на боевой сайт
  `https://ai-admin.azikonps4.workers.dev`. `main` целиком входит в `dev`, конфликтов нет.
- **Главное условие:** вместе с кодом подключить боевую базу D1 `ai-admin`. Без неё второй номер из пульта **не отправляет**
  («Отправка со второго номера не настроена…» — так задумано: без базы нет защиты от двойной отправки). Сегодня на боевом сайте
  второй номер отправляет по-старому, без базы, — поэтому выкладка без базы была бы шагом назад.
- **Порядок:** миграции и отметка базы → привязка `DB` в `main` → выкладка → проверки. Сначала база, потом код: если код выйдет
  раньше, пульт честно напишет «не настроена» (проверено), но администратор не сможет отвечать со второго номера из пульта.
- **Что не включается при запуске:** бот на обоих номерах, напоминания по журналу, рассылки со второго номера (раздел 4, шаг 6).
  Настоящая запись с сайта уже включена владельцем 29.10 (`SITE_BOOKING_WINCHESTER=1`), выпуск её не меняет.
- **Живая проверка до Кайрата** — на тестовом стенде `ai-admin-test` с запасным номером владельца (раздел 6).
- **Время:** 30–40 минут у компьютера (или в сессии Claude с подключением Cloudflare) и 15–20 минут проверки с телефона.

## 3. Решения владельца до запуска

1. **«Выкладывай»** — `dev` → `main` (боевой сайт).
2. **«Подключай D1»** — миграции на `ai-admin` и привязка `DB`.
3. **Основной номер в пульте — решено 01.11: не подключаем.** Основной WhatsApp Кайрата остаётся в WhatsApp Business на телефоне;
   настройки Wazzapo и Meta не трогаем, ссылки основного номера на winchester.kz не меняем. В пульте — один второй номер.
4. **Номера для живой проверки — решено 01.11:** телефона и второго номера Кайрата нет, поэтому проверка идёт на тестовом стенде

   временный: не объявлять номером барбершопа и не писать с него по базе Altegio.

По желанию, с разрешения владельца, — миграция 0005 на базу черновиков (не применялась: на черновике отправка со второго номера

### Шаг 2. Точка восстановления боевой базы

```sh
npx wrangler d1 time-travel info ai-admin
```

Записать закладку (bookmark) в заметки владельца — не в репозиторий. Помощник через подключение Cloudflare закладку сделать не
может: если миграции выполняет он (шаг 3, вариант Б), точкой служит пустая база — её можно пересоздать.

### Шаг 3. Миграции и отметка на боевой базе `ai-admin`

**Вариант А — компьютер с Node.js, вход `npx wrangler login`** (стандартный путь, `wrangler` сам ведёт учёт миграций):

```sh
git apply docs/runbooks/winchester-go-live-d1.patch   # привязка DB → ai-admin в рабочей копии (её же потом выкладываем)
npx wrangler d1 migrations apply DB --remote
npx wrangler d1 execute DB --remote --command "INSERT INTO meta (k, v) VALUES ('stage', 'production') ON CONFLICT(k) DO NOTHING"
npx wrangler d1 execute DB --remote --command "SELECT (SELECT v FROM meta WHERE k = 'stage') AS stage, (SELECT count(*) FROM d1_migrations) AS migrations, (SELECT count(*) FROM sqlite_master WHERE type = 'table' AND name = 'send_claims') AS send_claims"
```

Ожидаем: `stage = production`, `migrations = 6`, `send_claims = 1`. Миграции применяются по одной: 0001_messaging.sql,
0002_contacts_sync.sql, 0003_consent_evidence.sql, 0004_demo_source.sql, 0005_send_claims.sql, 0006_chat_storage.sql
(переписки в D1, 01.11.2026; включаются отдельно переменной `CHAT_STORE_WINCHESTER` — §8).

**Вариант Б — без компьютера: помощник Claude через подключение Cloudflare** (так обновляли базу черновиков 31.10). По слову
«подключай D1» помощник выполняет на базе `ai-admin` (id `ea1610ed-d342-41ca-8170-40ffe81feb41`, не путать с `ai-admin-dev`):

1. `CREATE TABLE IF NOT EXISTS d1_migrations(id INTEGER PRIMARY KEY AUTOINCREMENT, name TEXT UNIQUE, applied_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP NOT NULL)`
2. Для каждого файла по порядку — 0001_messaging.sql, 0002_contacts_sync.sql, 0003_consent_evidence.sql,
   0004_demo_source.sql, 0005_send_claims.sql, 0006_chat_storage.sql: текст файла целиком (строки-комментарии `--` можно убрать — так выполняли для базы
   черновиков), затем `INSERT INTO d1_migrations (name) VALUES ('<имя файла>')`. Ошибка на файле — остановиться: учёт показывает,
   какие уже применены.
3. `INSERT INTO meta (k, v) VALUES ('stage', 'production') ON CONFLICT(k) DO NOTHING`
4. Та же проверка `SELECT`, что в варианте А.

Повтор команды отметки ничего не меняет; если отметка оказалась не та (`preview`), команда её не перезапишет — это покажет
проверка, и базу нужно разбирать вручную.

## 5. Откат

1. **Код.** Cloudflare → Workers & Pages → ai-admin → Deployments → у предыдущей версии «⋯» → Rollback
   (или `npx wrangler rollback <id версии>`). Действует сразу. У прежней версии нет привязки `DB`: сайт работает, как до выкладки,
   второй номер из пульта отправляет по-старому.
2. **GitHub.** Revert коммита выкладки в `main` — иначе следующая сборка `main` вернёт новую версию.
3. **База D1.** Схему не откатываем: прежний код базу не читает, новые таблицы ничему не мешают. Данные (отметки отправок,
   события) остаются и пригодятся при повторном запуске.
4. **Если испорчены данные базы:** `npx wrangler d1 time-travel restore ai-admin --bookmark=<закладка шага 2>` — база целиком
   возвращается к закладке, всё записанное позже пропадает (Time Travel хранит 30 дней на платном тарифе).
5. **KV.** Новая версия только добавляет ключи (подписи линий, push, тексты сервисных сообщений); прежняя их не читает. Удалять
   ничего не нужно.
6. **Вебхук Green-API** ведёт на тот же боевой адрес — при откате его не трогаем.

## 6. Тестовый стенд `ai-admin-test`: живая проверка на номере владельца

Решение владельца 01.11: телефона и второго номера Кайрата нет — второй номер проверяется вживую на отдельном Worker
`ai-admin-test` с запасным номером владельца. Стенд не видит данных Winchester и не может написать никому, кроме тех, кто сам
написал на тестовый номер.

**Что в репозитории.** Папка `deploy/test-stand/` — свой `wrangler.jsonc`: имя `ai-admin-test`, код — тот же `worker.js`, свои KV и
D1, **без cron** (ни напоминаний, ни рассылок, ни синхронизации, ни сводок). Боевой `wrangler.jsonc` не меняется. Проверка —
`test/unit/test-stand.test.mjs`: в настройках стенда нет боевых и черновых id и нет cron; Worker ровно с переменными стенда не
отвечает ботом, не обращается к Altegio, Telegram, ИИ и Meta, не меняет вебхук чужого инстанса, не запускает рассылки и
напоминания, а ответ из пульта уходит один раз и только тому, кто написал.

| На стенде есть | На стенде нет — и не задавать |
|---|---|
