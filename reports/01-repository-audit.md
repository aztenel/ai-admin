## 2. Четыре основных кандидата

### 2.1. AureusERP v1.8.0 (Webkul) — `evidence/aureuserp.md`

**Что это.** Почти дословный перенос модели Odoo на Laravel 13 + Filament 5: quant / move / move line / lot / picking / POS-сессии. ≈405 тыс. строк PHP в 30 плагинах (`plugins/webkul/*`), каждый — отдельный composer-пакет (`wikimedia/composer-merge-plugin`).

**Сильные стороны.**
- Полный набор модулей «из коробки»: склад (1–3-шаговые приёмки/отгрузки, внутренние перемещения, возвраты, списания, резервы, инвентаризация, журнал движений), закупки, продажи, POS с кассовыми сменами и офлайн-черновиками, бухгалтерия, счета, платежи, CRM, сотрудники.
- MIT — можно закрывать свой код и продавать по подписке.
- POS идемпотентен: уникальный `uuid` заказа + `lockForUpdate` в транзакции (`point-of-sale/src/Services/OrderProcessor.php:49,216-222`) — **подтверждено тестом PM-09**.
- Нумерация документов без гонок (`support/src/Services/SequenceService.php:66-127`).
- 884 теста склада и 335 тестов POS **проходят** на PostgreSQL 16 (отчёт 05).
- REST API на Sanctum с документацией Scribe, права через filament-shield + политики на каждый ресурс, TOTP-2FA.

**Слабые стороны (для магазина телефонов — критичные).**
- **Нет уникальности серийника (IMEI)** ни в базе, ни в проверках: `inventories_lots.name` — только индекс (`inventories/database/migrations/2025_01_14_092601_create_inventories_lots_table.php`), `LotRequest.php:20`, `LotForm.php:32`. Тест PM-08: три записи с одним IMEI.
- **POS продаёт, даже если IMEI нет на складе или он уже продан**: `PickingGenerator::forceComplete()` откатывает только складскую часть, заказ всё равно «оплачен» (`point-of-sale/src/Services/PickingGenerator.php:144-174`, `OrderWorkflow::markPaid()`). Вживую: повторная продажа того же IMEI проходит, остаток −1 (PM-02); продажа выдуманного IMEI создаёт новый лот (PM-04); две одновременные продажи одного IMEI проходят **10 из 10 раз** (отчёт 05).
- Отрицательные остатки разрешены (`ProductQuantity::adjustStock(... allowNegative: true)`), запрета в настройках нет.
- Workflow-методы REST API (validate/cancel/reserve/return) без транзакции (`inventories/src/Http/Controllers/API/V1/OperationController.php:115-147`) — возможны частичные записи.
- Себестоимость одна на товар (`products_products.cost`), себестоимости единицы (IMEI) и FIFO нет.
- Мультикомпания, а не SaaS: строки с `company_id = NULL` видны всем компаниям, scope выключен в консоли и очередях, роли глобальные (`support/src/Models/Scopes/CompanyScope.php`, `config/permission.php:126 teams=false`).
- Импорта товаров/остатков/серийников нет (импорт есть только в CRM).
- Безопасность: токены Sanctum бессрочные (`config/sanctum.php:53`), `trustProxies('*')`, вложения chatter на публичном диске, в репозитории лежит `.env.pgtest` с `APP_KEY`, debugbar в `require`.
- Установка «с нуля» хрупкая: в lock-файле пакет `phpstan/phpstan` без source — без доступа к архивам GitHub `composer install` не проходит (обошли правкой локального lock, отчёт 05).

**Оценка как основы:** сильный донор модулей и UI-паттернов на Laravel/Filament; как ядро учёта IMEI без переделки ядра POS и склада — **непригоден**.

### 2.2. Inventoros v2.3.0 — `evidence/inventoros.md`

**Что это.** Самостоятельно размещаемая система склада и заказов (Laravel 13, Inertia + Vue 3), учёт прежде всего количеством, опциональная мультиорганизация.

**Сильные стороны.** Лучшая среди PHP-кандидатов дисциплина конкурентности: каждое изменение остатка — в транзакции с блокировкой строк, переходы статусов перечитывают запись под блокировкой (`StockAdjustment::adjust()`, сервисы заказов/закупок/перемещений/возвратов). Изоляция организаций: глобальный scope на 28 моделях (`OrganizationScope.php:28-53`), ~20 тестов изоляции, подписанные исходящие вебхуки с защитой от SSRF, REST + GraphQL + MCP, импорт/экспорт Excel.

**Слабые стороны.**
- **AGPL-3.0-only** с v1.0.9: закрытый SaaS на его коде обязан отдавать исходники каждому пользователю сети. Коммерческой лицензии нет. MIT-версия v1.0.8 — без большей части укреплений.
- Серийники вторичны: `products.stock` — источник правды, серийники «могут молча расходиться» (`TrackedStockReconciliationService`); у серийника нет склада, варианта и себестоимости; кассир не выбирает IMEI — система берёт самый старый (`TrackedStockAllocationService.php:102-141`); возврат освобождает не тот IMEI (`ReturnOrderService.php:645-655`).
- Нет POS, нет KZT, нет казахского, PDF на Helvetica (кириллица, вероятно, сломана — статически).
- Остаток проверяется по всей организации, а не по филиалу (`OrderService.php:197-212`).
- Требует PHP 8.4.

**Оценка:** образец архитектуры блокировок и изоляции; как основа коммерческого закрытого продукта — **нельзя по лицензии**.

### 2.3. Bagisto (2.5.x-dev) — `evidence/bagisto.md`

**Что это.** Интернет-магазин на Laravel (Webkul). Типы товаров: простой, конфигурируемый, виртуальный, групповой, комплект, загружаемый, бронирование.

**Сильные стороны.** Оформление заказа в транзакции с блокировкой остатка (`OrderItemRepository::manageInventory`, стр. 108-131), повтор до 3 раз; ACL на каждом маршруте админки (`Bouncer.php::checkIfAuthorized`); 2FA админа; RMA-возвраты; полный русский перевод; KZT в установщике; конфигурируемые товары «модель → память/цвет» удобны для витрины телефонов.

**Слабые стороны.** Нет учёта по единицам (IMEI — 0 совпадений), закупок, поставщиков, перемещений, инвентаризации, журнала действий; POS и SaaS-мультиарендность — платные расширения (кода нет); после заказа отгрузка/отмена/возврат меняют остаток без блокировок; отмена заказа без транзакции (`OrderRepository::cancel`, 141-196); нет казахского языка и Kaspi.

**Оценка:** как ERP — **не подходит**; как отдельная витрина поверх нашей ERP — **возможно** (стратегия C), с доработкой kk, Kaspi и синхронизации остатков.

### 2.4. ERPNext — `evidence/erpnext.md`

**Что это.** Самая зрелая открытая ERP (Frappe). Все нужные документы есть: Purchase Receipt, Delivery Note, Sales Invoice со списанием, POS Invoice со сменами, Stock Entry (Material Transfer, в том числе транзит), Stock Reconciliation, возвраты `is_return`, отмена с обратными проводками, Stock Reservation, Warranty Claim, Maintenance Visit, полная бухгалтерия.

**Сильные стороны.** Серийник — полноценная сущность со статусом, складом, себестоимостью, датой конца гарантии; проверка «нельзя продать то, чего нет на этом складе» с `SELECT … FOR UPDATE` по строкам Serial No (`serial_and_batch_bundle.py:276, 2678, 2782`). Вживую (v15): повторная продажа, продажа в двух процессах одновременно — см. отчёт 05. Огромное сообщество, 7 970 тестов, REST/вебхуки/импорт из Frappe, кастомизация своим приложением через `hooks.py` без форка.

**Слабые стороны.**
- Уникальность серийника — по паре (товар, номер), не глобально (`serial_batch_identity.py:27-36` в develop); IMEI2 — только Custom Field; сканер по нему не ищет.
- POS Invoice не двигает склад до закрытия смены; занятые номера читаются без блокировки (`get_reserved_serial_nos_for_pos`, 2965) — статически возможна гонка двух кассиров.
- Мультиарендность Frappe = отдельный сайт с отдельной базой на каждого клиента: сотни баз, миграции по каждой.
- Нет Казахстана: ККМ/ОФД, ЭСФ, казахский язык.
- Тяжёлая эксплуатация (Python + MariaDB + Redis + Node + воркеры), ежегодные мажорные версии ломают совместимость (пример — смена модели Serial No в v15 и снова в develop).
- GPL-3 (без сетевого условия) + запрет слова «ERPNext» в продукте/домене/рекламе (`TRADEMARK_POLICY.md`).
- Установка: `bench init` не работает от root; фронтенд-зависимости Frappe тянутся архивами с GitHub (в этой среде закрыты) — бэкенд поставлен в обход (отчёт 05).

**Оценка:** лучшая готовая функциональность и самая надёжная модель серийника из «полных» ERP; цена — другой стек (Python/Frappe), GPL, тяжёлая мультиарендность, нет казахстанской специфики.

## 5. Пробелы этого аудита

- Не проверены вживую: Bagisto, Odoo, Dolibarr, Tryton, OSPOS (статический анализ).
- ERPNext запущен на `version-15`, а статический аудит — на develop (17.0-dev); модель Serial No между ними отличается (имя записи = номер в v15, хэш в develop).
- Нет звёзд/issues с GitHub (API закрыт в сессии).
- Frappe Framework не клонирован для статического аудита; выводы о нём помечены в `evidence/erpnext.md` как «по знаниям».
