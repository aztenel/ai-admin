- `wrangler.jsonc` — конфигурация заливки. `keep_vars: true` обязателен: переменные и секреты заданы в панели Cloudflare. `triggers.crons` — фоновая задача раз в минуту (рассылки).

## Платформа: конвейер ботов (сделана в ветке `dev`, вживую ещё не проверена)
Один общий движок + «паспорт бота» (данные клиента в хранилище, код не правится) + одинаковые проверки для каждого бота.
- **Паспорт бота.** Все паспорта лежат в KV одним ключом `cfg:all` (`{ <id>: cfg }`). `compileClient(cfg)` превращает паспорт в объект клиента (как в `CLIENTS`): разбирает график (`parseSchedule`), услуги (`parseServices`), мастеров, берёт тексты ниши из `NICHES`. `syncClients(env)` подгружает паспорта в начале каждого запроса (не чаще раза в минуту на экземпляр). Паспорт с ошибками в бота не превращается. Встроенные демо (`BUILTIN`) паспортом не заменяются.
- **Секреты клиента — только в Cloudflare**, по имени: `WA_TOKEN_<ID>`, `APP_SECRET_<ID>`, `PHONE_NUMBER_ID_<ID>` (или поле паспорта `waPhoneId`), `TG_CHAT_<ID>` (или `tg` в паспорте), `KEY_<ID>`, `ALTEGIO_LOC_<ID>`; Green-API — `GA_ID_<ID>`, секрет `GA_TOKEN_<ID>`, `GA_URL_<ID>` (apiUrl из кабинета, по умолчанию `api.green-api.com`). В паспорт и в репозиторий секреты не попадают.
- **Вход.** Ключ вводится один раз → cookie `aia` на 30 дней (HttpOnly, Secure, SameSite=Lax; подпись HMAC от `LEADS_KEY`). Владелец входит ключом `LEADS_KEY`; сотрудник клиента — своим ключом (в паспорте хранится только его хеш `keyHash`; смена ключа гасит старые сессии). Сотрудник видит только своего клиента (`canSee`). Все изменяющие запросы проверяют источник (`sameOrigin`). Страницы отдаются через `page()` (без кэша, без встраивания).
- **Страницы:** `/studio` — «Мои боты» (только владелец): форма паспорта, проверка, ключ сотрудника. `/launch?c=<id>` — проверка запуска: чек-лист подключений и экзамен бота на живой модели (сценарии собираются из паспорта, `casesFor`). `/inbox?c=<id>` — пульт чатов. `/broadcast?c=<id>` — рассылки. `/leads` открывается и по cookie.
- **WhatsApp на несколько клиентов:** вебхук `/wa/<id>`. Подпись Meta обязательна (`APP_SECRET_<ID>`), ответ уходит токеном `WA_TOKEN_<ID>` с того номера, на который написали (`metadata.phone_number_id`). Прежний режим (один номер на воркер: `POST /`, `WA_TOKEN`, `WA_CLIENT`) работает как раньше. Вебхук обрабатывает все сообщения пачки (`WA_BATCH`), остальные кладёт в пульт с пометкой.
- **Green-API (обычный WhatsApp по QR-коду) на несколько клиентов** (`gaRoute`): вебхук `/ga/<id>?t=<пароль>`; пароль — HMAC от токена инстанса (`gaHook`), отдельного секрета нет. «Проверка запуска» показывает состояние номера и кнопку «Настроить Green-API» (`/api/launch/ga` → `setSettings`: адрес вебхука этого сайта, входящие, ответы с телефона, состояние номера; инстанс перезапускается до 5 минут). Сообщение с чужого инстанса (`instanceData.idInstance`) не обрабатывается. Ответ с телефона виден в пульте и ставит бота в чате на паузу. Пульт отвечает с номера клиента. Прежний общий номер (`GA_ID`, `GA_TOKEN`, `GA_HOOK`, `GA_CLIENT`, вебхук `/ga?t=<GA_HOOK>`) работает как раньше.
- **История чата** — один ключ `h:<канал>:<клиент>:<id>`: `{ n, turns: [{ role, text, t, by?, m? }], profile }`. Хранится `HIST_KEEP` (60) реплик, в ИИ уходит `MAX_TURNS` (24). Метаданные ключа (`histMeta`) — это строка списка чатов в пульте: список читается одним `KV.list` без чтения чатов. Писать историю только через `putHist`/`logTurns`.
- **Пульт чатов.** `profile.need = { at, why }` поднимает чат в «Ждут ответа» (`human`, `limit`, `media`, `ai`, `req`, `lead`, `call`, `off`). Ответ администратора (`by: "admin"`) ставит бота в этом чате на паузу на 2 часа; есть «Вернуть бота», «Остановить на 12 часов», «Сделано → сообщить клиенту» для просьб об отмене и переносе (заявка получает статус «выполнена», запись убирается из `profile.bookings`). Писать клиенту можно только в 24-часовом окне WhatsApp (`profile.li`). В чат на сайте ответить нельзя.
- **Рассылки** (раздел «РАССЫЛКИ» в конце `worker.js`). Через Meta — только шаблоны, одобренные Meta (через Green-API — обычный текст, см. ниже). Отправляет фоновая задача: `scheduled` → `cronRun` раз в минуту (cron в `wrangler.jsonc`; у черновиков cron не работает — на странице есть кнопка «Отправить порцию сейчас»). Правила: порция отмечается отправленной **до** отправки (никто не получает сообщение дважды; оборванная порция помечается «неизвестно»); тем, кто в списке `optout:<клиент>:<номер>`, не шлём («стоп» боту, отказ от рекламы в WhatsApp, кнопка «Остановить рекламу»); предел на скользящие 24 часа общий для клиента (`bcq`); часы отправки 8–22. Ошибки Meta: `BC_TEMP` — ждать 10 минут, `BC_ACCOUNT` — пауза и получатель обратно в очередь, `BC_PARAM` — пауза, со второго раза получатель пропускается, пять ошибок подряд — пауза. Сигналы Meta с вебхука (`waSignal`: шаблон приостановлен, качество упало, аккаунт ограничен) ставят рассылки на паузу (`bchold`). Текст последней рассылки (`bclast`) 7 дней виден ИИ в чатах WhatsApp и администратору в пульте. Меняешь эту часть — сначала сценарий в `test/platform.mjs`.
- **Рассылки через Green-API** (`b.ch = "ga"`, обычный текст; на заглушках проверено, вживую — нет). Такой номер WhatsApp блокирует за массовые рассылки, поэтому: по одному сообщению, пауза 30–150 секунд (`nextAt`, `GA_GAP`); с номера одного клиента — не больше одного сообщения за запуск фоновой задачи; предел 1–300 в сутки (по умолчанию 50), счётчик свой у номера (`bcq:<клиент>:ga`); в конце текста бот сам добавляет «ответьте СТОП», если про «стоп» в тексте ничего нет (`bcGaMsg`); картинка — `sendFileByUrl` с подписью до 1024 знаков. Запуск — только если номер привязан и вебхук ведёт в этот бот (иначе «стоп» клиентов не дойдёт до бота). Перед каждым сообщением `getStateInstance`: `notAuthorized` — пауза («отсканируйте QR»), `blocked`/`suspended`/`yellowCard` — пауза и пометка `bchold.ga` (продолжить — только с подтверждением), `sleepMode`/`starting` — ждать 10 минут. Ошибки (`gaKind`): 429, 5xx — ждать 10 минут; 400 — пропустить номер; нет ответа — номер не повторяется; 401, 403, 466 (кончился тариф), истёкший инстанс — пауза. Вебхук: `stateInstanceChanged` (блокировка, ограничение — тревога в Telegram), `outgoingMessageStatus` (`noAccount`, `failed` — в счёт недоставленных). Сигналы Meta не трогают Green-API, и наоборот.
- **KV пишет один ключ не чаще раза в секунду** (иначе отказ 429). Любая запись «прочитал → изменил → записал» в ключ, который могут писать два запроса подряд, идёт через `kvRetry`. Проверить новое место: `KV_STRICT=1 node test/platform.mjs` (строгий KV; из-за секундных пауз часть сценариев в нём не проходит — смотреть нужно на необработанные отказы).
- **Проверки платформы:** `test/harness.mjs` — обвязка (KV в памяти с метаданными, заглушки Gemini, Telegram, Meta, Altegio, Green-API (`net.ga` — запросы, `net.gaState`, `net.gaSettings`, `net.gaReply`); `mk()` → сайт с помощниками, `S.cron()` — фоновая задача). `test/platform.mjs` — проверки новых частей (запускается из `test/smoke.mjs`). `test/devserver.mjs` — локальный сервер на заглушках (`node test/devserver.mjs`, вход ключом `owner-key-123456`). `test/e2e.mjs` — сценарий в настоящем браузере (Playwright, в `npm test` не входит): `node test/e2e.mjs <папка для снимков>`.
- **Известные ограничения:** гонки KV (два сообщения одного чата одновременно; две страницы владельца, сохраняющие разные паспорта; фоновая и ручная отправка рассылки в одну и ту же секунду) — полностью закрываются только Durable Object; бесплатный тариф Cloudflare (1000 записей и 1000 списков KV в сутки, 10 мс процессора) для настоящего клиента с WhatsApp мал — перед запуском нужен платный ($5). Рассылка через Green-API тратит около 5 записей и одного списка KV на сообщение.

## ИИ (Gemini) — скорость и «связь прервалась»
- Вызов — `askGemini`. Модели: `MODEL` (по умолчанию `gemini-flash-lite-latest`) → запасная `MODEL_FALLBACK` (`gemini-flash-latest`). Таймаут одной попытки 9 с; если ответа нет, пробуется запасная модель; когда не ответили обе — клиент видит «связь прервалась» (`cut off|timeout` в `think()`).
- «Раздумья» модели (thinking) — главная причина медленных ответов и обрывов: «мысли» входят в лимит токенов. Поэтому у модели есть лесенка настроек `THINK_LADDER` (Gemini 2.5 — `thinkingBudget: 0`; остальные — `thinkingLevel: "minimal"` → `thinkingBudget: 0` → `thinkingLevel: "low"` → без настройки). Если Gemini отвечает 400 со словом thinking, берётся следующая ступенька той же модели; принятая запоминается (`THINK_STEP`). Запас на ответ — 2048 токенов. Ответ, оборванный по лимиту, клиенту не уходит: пробуется запасная модель.
- Второй и третий запрос к ИИ в одном сообщении делаются, когда защита отклонила черновик или в нём «записала» без служебной строки: время ответа тогда складывается из двух-трёх вызовов.
- `/diag?key=…` меряет каждую модель на настоящей подсказке бота: миллисекунды, настройка «раздумий», токены «мыслей», чем кончился ответ. Быстро — до 4000 мс. **Скорость вживую из облачной сессии не проверить** — смотреть на `/diag`.

- **Выбор модели (замер 8 октября 2026, цены по сайтам OpenRouter и Anthropic, на вживую не проверялись).** Вживую: на `gemini-flash-lite` ответы шли 17–24 с с «связью прервалась» (на боевом `/diag` — timeout), на `gemini-3.5-flash` стало 3–5 с, ответы заметно лучше. Но `gemini-3.5-flash` стоит $1,50 / $9 за 1 млн токенов (по умолчанию «думает», «мысли» платные): по прикидке для одного барбершопа (≈7 000 запросов в месяц, ≈10 тыс. токенов на вход) около $118 (≈52 000 ₸ при 441 ₸/$) — слишком дорого для цены 150 000 ₸. Кандидаты дешевле: Claude Haiku 5.5 и GPT-6 Luna ($0,10 / $0,50, ≈$8 в месяц), DeepSeek V4.1 Flash ($0,15 / $0,60, в пик вдвое дороже; данные клиентов уходят в Китай, задержку не проверяли). Бенчмарки в сети — про код и агентов, не про диалог на русском и казахском: выбирать по нашим сценариям (`/selftest`, экзамен на `/launch`). План: после запуска первого клиента добавить в `askGemini` других поставщиков (Anthropic, OpenAI-совместимые), переключение одной переменной, прогнать сценарии на всех. Пока на демо — `MODEL=gemini-3.5-flash`.
- **Claude как поставщик ИИ (в `dev`; вживую на черновиках 10 октября: ответы 1–3 с, `/diag` ~1,1 с на настоящей подсказке).** `MODEL=claude-haiku-5-5` (имя на `claude-…`) + секрет `ANTHROPIC_KEY` (console.anthropic.com, отдельно от подписки Claude) — `askGemini` для таких моделей зовёт `askClaude` (Messages API, 9 с, 529/5xx — повтор, 400 про temperature — повтор без неё, обрыв по `max_tokens` и любой отказ — следующая модель списка). Бесплатный ключ Gemini для настоящих клиентов не годится (по правилам Google такие тексты могут идти на улучшение их продуктов).

Только записи, созданные ботом в Altegio, только WhatsApp (`wa` — в 24-часовом окне, `ga` — всегда). Поле `remind`: пусто — оба, `day` — только накануне, `off`. Очередь `rmq:<клиент>`, список `rmidx`, отметка `rms:<клиент>:<запись>:<вид>` до отправки; перед отправкой перечитывается чат (запись на месте, без `rq`, нет «стоп»). Опоздавшие больше 3 часов не уходят. **У черновиков фоновой задачи нет — вживую не проверено.**
- **Ремонт техники**: ниша `repair`, поле `repairs` — прайс «модель | работа | цена | срок» до 300 строк (`parseRepairs`, цены «45000», «от 30000», «45000–60000», «бесплатно», «после диагностики»), в факты отдельным блоком (свой предел, `facts0Len`), правило `REPAIR_RULE` (вилка только из прайса, всегда «предварительно, точно — после диагностики»), сценарий экзамена «Оценка ремонта». Бот без записи (`booking: none`) в запасном ответе просит имя и телефон (`safeAsk`).
- **Рассылки по сегментам**: в списке получателей даты (`bcDate`): по заголовку Excel («Последний визит», «День рождения») или по году (свежая — визит, давняя или без года — день рождения). `seg`: `idle` (не были дольше N дней) или `bday` (день рождения в ближайшие N дней), N 1–365 (`bcSeg`); в рассылке хранится `seg`.
- **Altegio, живая проверка 10 октября** (пробная локация 1399687, бот `kairat` на черновиках): чтение услуг и мастеров, запись (в т. ч. двоих), просьба об отмене администратору, Telegram — работают. Исправлено: после просьбы об отмене вопрос о другом («как оплатить?») получал «в расписании ничего не изменилось» — теперь ответ ИИ остаётся, убирается только ложная фраза об отмене. В подсказке: услуга на нескольких человек («Папа + Сын») — одна запись.
- **Записи, удалённые в Altegio** (`altPrune`, перед подсказкой): каждая будущая запись чата проверяется `GET /user/records/<id>/<hash>`; удалённой считается, если Altegio ответил `deleted` или 404 «не найдена». Если чтение записи не ответило (ключом партнёра может быть недоступно), смотрим время мастера (`altTimes`, свежий запрос): время записи снова свободно — записи нет. Сбой — запись остаётся. В заглушках: `net.altGone`, `net.altBusy`, `net.altGetFail` (`test/harness.mjs`), `ALT.gone` (`test/smoke.mjs`); стабы `test/review` отвечают на чтение записи «на месте». Формат ответа Altegio на удалённую запись **вживую не проверен**. Вживую 10 октября бот всё равно говорил об удалённой записи: текст «Уже известно о клиенте» не пересчитывался (ошибка `bookedText is not defined` в `altPrune`, исправлено — пересчёт в `think()`). Чтение записи «успешно», но без поля `deleted` считается «не знаем» → проверка по времени мастера. На `/altegio` после «Пробной записи» строка «Чтение удалённой записи» показывает, что Altegio отвечает на удалённую запись.
- Проверка «удалена ли запись» — `altIsGone` (общая для `altPrune` и возврата записи по старой заявке). Вживую 10 октября (demo6): память чата очистили, запись удалили в Altegio, клиент снова записывается — бот по старой заявке (`viewLeads`, «ghost») вернул запись и ответил «Вы уже записаны». Теперь перед возвратом спрашиваем Altegio; удалённая — заявка «отменена» (примечание «запись удалена в Altegio»), записи, забытые `altPrune`, тоже (`profile.altGone`). Мастер записи неизвестен — удалённой считается, если её время свободно у всех мастеров.
- **Удалённые в Altegio записи — по времени мастера** (вживую 10 октября на `/altegio`: чтение записи — 405; пока запись есть, время мастера «занято» и `book_check` не проходит (422), после удаления — «свободно» и проходит). Удалённой запись считается, только если сходятся оба признака и запись создана больше 5 минут назад (`ALT_GONE_AGE`; на demo7 через минуту после записи бот ошибочно её «забыл» — причина не выяснена). Мастер неизвестен — время должно быть свободно у всех мастеров. Выключить — Text `ALTEGIO_SLOT_CHECK` = `0`. В заглушках: `net.altBusy` (занятое время и `book_check` 422), `net.altCheckBusy`. «Очистить память бота» ставит `profile.forgot` (старые заявки чата в чат не возвращаются) и обнуляет дневной предел записей этого номера (`bk:<локация>:<номер>:<день>`).
- **Ключ пользователя Altegio (журнал записей) — проверка** `/altegio/user?c=<id>` (только владелец): логин и пароль Altegio → `POST /auth` → `user_token` (не сохраняется, на страницу не выводится), затем журнал `GET /records/<локация>` или `/locations/<локация>/appointments` с заголовком `Bearer <партнёр>, User <ключ>` и пробная запись: видна ли в журнале, что после удаления. `altCall(env, method, path, body, user)`. Формат ответов в заглушках выдуман — **вживую не проверено**.
- **«Любой мастер»**: бот сам выбирает мастера, у которого это время свободно (из них — у кого день свободнее; при 2–12 мастерах), записывает к нему и называет его клиенту. Раньше Altegio назначал мастера сам, а бот говорил «мастер не прикреплён». В подсказке: если клиент мастера не назвал — один раз спросить, к кому записать (правила К и Л). Пульт: «Очистить память бота» (`act: forget`) — бот забывает переписку и записи чата, окно WhatsApp и «стоп» остаются.
- **Черновики и Green-API**: вебхук Green-API ведёт в тот черновик, где последний раз нажали «Настроить Green-API» — после нового черновика нажимать снова. Новые переменные «Previews Base» видит только новый черновик (новая ветка).
- CI (`.github/workflows/checks.yml`) гоняет `test/smoke.mjs` на Node 20, 22 и 24.

## Altegio
- Используется публичный API онлайн-записи (`api.alteg.io/api/v1/book_*`): нужен только ключ разработчика (секрет `ALTEGIO_PARTNER` в Cloudflare) и номер локации клиента. Справочник: developer.alteg.io/en/public/openapi/online-booking.
- Справочнику верь не до конца, проверяй вживую. Проверено на настоящем Altegio (3 октября 2026, пробная локация): чтение услуг, мастеров, дат и времени; `book_check`; создание записи и её удаление. Создание без поля `email` отвечает 422, хотя в справочнике поле необязательное, — бот передаёт его пустым (`altRecord`). Номер с «+» принимается. Длительность услуги (`seance_length`) в `book_services` без мастера не приходит.
- Локация клиента: `altegio.location` в его блоке `CLIENTS` или переменная `ALTEGIO_LOC_<ID>`. Тестовый клиент `alt` скрыт с витрины.
- **Два режима отмены и переноса** (`altSelfCancel`). По умолчанию — **режим администратора**: бот в расписании ничего не удаляет; просьбу клиента об отмене или переносе он передаёт администратору заявкой (`kind: "cancel"` или `"change"`, видна на `/leads`) и сообщением в Telegram, клиенту отвечает «передала администратору» (`cxAdmin`, `mvAdmin`). Так запускаем первого заказчика. Второй режим — бот отменяет и переносит сам: Text `ALTEGIO_SELF_CANCEL` = `1` (или `ALTEGIO_SELF_CANCEL_<ID>`, или `altegio.selfCancel` в блоке клиента). Не включать, пока не сделано правило «перед любой отменой бот переспрашивает» и не пройдена ещё одна независимая проверка.
- Режим администратора: просьба уходит, когда об отмене или переносе просил сам клиент (`wantsChange`) и ИИ это подтвердил — строкой `[ОТМЕНА]`, словами «отменила» или «передала администратору» (`ADMIN_CX`). ИИ поставил `[ОТМЕНА]` без просьбы клиента — ничего не происходит. Пара строк `[ОТМЕНА]` + `[ЗАЯВКА]` на уже записанного человека — просьба о переносе (новую запись бот не создаёт), кроме случая, когда клиент сказал «ещё». Запись, которой нет в чате, — тоже заявка (с телефоном). Клиент передумал или снова записывается на то же время — администратору «клиент передумал». Одна просьба — одна заявка (`profile.req`), записи с просьбой помечены `rq`.
- Клиент передумал («не надо отменять», «оставьте запись») — администратору уходит «клиент передумал», а заявка-просьба на `/leads` получает статус «клиент передумал». Клиент снова записывается на то же время — бот напоминает о просьбе и подсказывает написать «оставьте запись» (сам ничего не решает).
- Частица «не» в правилах просьб (`ALT_WANT_CHANGE`, `ALT_KEEP`, `ALT_UNDO`, `MOVE_WISH`) — только отдельным словом (`(?<![а-яё])не`). Без этого «мне нужно отменить запись» читалось как «не нужно отменять». Добавляешь правило с «не» — ставь эту границу и пример в тесты.
- Всё, что ниже про отмену и перенос самим ботом (`samePerson`, `cxAsk`, «да» отменяет), относится к режиму `ALTEGIO_SELF_CANCEL`. Старые проверки (`test/smoke.mjs` до раздела «режим по умолчанию», `test/review/`) идут в этом режиме.
- Итог записи, отмены и переноса клиенту сообщает код (`altSay`) по ответу Altegio, а не текст ИИ. ИИ только ставит служебные строки `[ЗАЯВКА]` и `[ОТМЕНА]`. Фразы ИИ «записала / отменила / перенесла» без служебной строки до клиента не доходят (`altClaims`). Если после изменений фильтр начал портить обычные ответы или пропускать ложные — правь списки `CLAIM_*` и `CL_*` и добавляй пример в тесты.
- Активные записи чата — в `profile.bookings`, заявки, которые ждут администратора, — в `profile.pend`. Перенос = `[ОТМЕНА]` + `[ЗАЯВКА]` в одном ответе: сначала создаётся новая запись, потом удаляется старая.
- Отмена удаляет только запись из этого чата, названную в строке отмены. Имена сравниваются строго (`samePerson`): «Жанар» ≠ «Жанат», «Тимур Ахметов» ≠ «Тимур Иванов»; латиница и казахские буквы приводятся к русским («Timur» = «Тимур», «Айгүл» = «Айгуль»).
- Бот не удаляет запись молча, если есть сомнение: строка `[ОТМЕНА]` без подробностей, а клиент назвал другое имя, день или время; имя в строке не совпало; строка была в ответе, который отклонила защита. Тогда бот спрашивает «Отменить запись …?» и запоминает вопрос (`profile.cxAsk`); ответ «да» отменяет именно эту запись, что бы ни написал ИИ.
- Телефон берётся только у клиента (из его сообщения или номера WhatsApp), а не из строки ИИ.
- Названия услуг и имена мастеров из Altegio очищаются (`altText`): знаки `; | [ ] { } :` ломают разбор служебных строк. Услуга и мастер подбираются так: не уверены — переспрашиваем, а не угадываем (`altPickServices` → `{list}` или `{ask}`, `altPickStaff` → `{staff}`, `{any}` или `{ask}`). «Не Арман» и «любой, кроме Армана» — это не «любой».
- Поля служебных строк (`tagFields`) читаются и с ключами на английском и казахском, с разными разделителями; дата — в нескольких видах (`altDateOf`).
- Если Altegio не принял запись или недоступен, бот не теряет клиента: создаёт заявку администратору с пометкой. Если свободного времени нет совсем — заявку на обратный звонок (не чаще раза в час на чат; в браузер от неё уходит только телефон). Заявок администратору из одного чата — не больше 6 в сутки.
- Лимиты автоматических записей: 4 на чат, 5 в сутки на телефон, 15 в сутки на IP, 60 в сутки на локацию; сверх лимита — заявка администратору. Перенос записи лимиты не тратит.
- WhatsApp без подписи Meta (`APP_SECRET` не задан): бот сам в расписание не записывает.
- Заявки, история чата и уведомления сохраняются в конце сообщения в таком порядке: заявки → история → ответ клиенту → Telegram (`opts.defer`). Сбой хранилища не должен ронять ответ клиенту.
- Заявка хранится дважды: в общем списке `leads:<клиент>` и отдельным ключом `lead:<клиент>:<день>:<id>` (`leadKey`). Общий список может потерять заявку, когда два чата пишут его одновременно; страница `/leads` возвращает такие заявки из отдельных ключей за последние 7 дней (`allLeads`).
- Страховка от ошибок в коде: разбор ответа ИИ обёрнут в `try` (клиент получает «передала администратору», администратор — сигнал), вокруг всего `think()` — `thinkSafe`.
- Два сообщения одного чата одновременно: при сохранении история сливается (`mergeProfile`). Полной защиты от гонки нет — для неё нужен Durable Object.
- `/altegio?key=<LEADS_KEY>[&loc=<номер>]` — что бот видит в Altegio. Кнопка «Пробная запись» создаёт запись и сразу удаляет её.
- Вживую с настоящим Altegio проверяй после каждого изменения этой части: страница `/altegio` и чат `/?c=alt`. Страница `/altegio` показывает и режим отмены, и настроен ли Telegram.
- Без Telegram (`TG_TOKEN`, `TG_CHAT`) запускать клиента нельзя: в режиме администратора отмены и переносы приходят именно туда (без него они видны только на `/leads`).

## Правила
- Ветка `main` = боевой сайт: Cloudflare Workers Builds выкладывает каждый коммит в `main` (сначала `node test/smoke.mjs`, потом `npx wrangler deploy`).
- Любая ветка, кроме `main`, = черновик: Cloudflare собирает для неё отдельный адрес (`npx wrangler preview`, Worker Previews), рабочий сайт не меняется. Новое делай в `dev`.
- Для черновиков в `wrangler.jsonc` обязателен блок `previews` (без него сборка падает). Черновик не наследует настройки рабочего сайта: хранилище KV прописано в `previews` (то же, что у рабочего сайта), переменные и секреты — в панели: Settings → Previews. Новый секрет в панели получают только новые черновики (новая ветка).
- Адрес черновика ветки `dev` по документации Cloudflare: `https://dev-ai-admin.azikonps4.workers.dev`.
- Перед `main`: `npm test` (на Node 20 и 22) и сравнение со старой версией для клиентов без Altegio. После выкладки — живой автотест: `/api/selftest?key=<LEADS_KEY>&i=<номер>`.
- Результат сборки виден без панели: `gh api repos/aztenel/ai-admin/commits/<sha>/check-runs`.
- Никаких ключей, токенов и паролей в репозитории и в чате.
- Репозиторий публичный: отчёты проверок с ещё не исправленными слабыми местами в него не кладём.
- После выкладки проверяй вживую: `/`, `/?c=barber`, `/privacy` на https://ai-admin.azikonps4.workers.dev.
- Не обещай владельцу и его клиентам то, что не проверено вживую.
