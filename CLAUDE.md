## Проект
- `worker.js` — весь бот: один Cloudflare Worker (веб-чат, WhatsApp Cloud API, Green-API, автотест `/selftest`, `/diag`, `/leads`, `/privacy`).
- `test/smoke.mjs` — сценарии на заглушках (KV, Gemini, Telegram, Meta и Altegio подменены). Запуск: `npm test`. `SHOW=1 npm test` — показать ответы бота.
- `test/clock.mjs` — часы проверок закреплены: суббота 3 октября 2026, 12:00 по Астане (свободные окна демо-клиентов зависят от даты).
- Каждую найденную ошибку сначала повтори сценарием в `test/smoke.mjs`, потом исправляй: без сценария она возвращается.
- `test/review/` — около 130 сценариев от независимых проверяющих (в `npm test` не входят, идут две минуты). Запуск: `node test/review/run.mjs`. Запускай перед выкладкой, если менялась запись в Altegio, разбор ответа ИИ или защита ответа. Что значат пометки — в `test/review/README.md`.
- Живой автотест (`/selftest`, `/api/selftest?key=…&i=N`) включает сценарии с настоящим расписанием Altegio: запись в них только проверяется (`book_check`), в журнале ничего не появляется. Ответы живой модели меняются от запуска к запуску: один непрошедший сценарий сначала перезапусти.
- `wrangler.jsonc` — конфигурация заливки. `keep_vars: true` обязателен: переменные и секреты заданы в панели Cloudflare. `triggers.crons` — фоновая задача раз в минуту (рассылки).

## Платформа: конвейер ботов (сделана в ветке `dev`, вживую ещё не проверена)
Один общий движок + «паспорт бота» (данные клиента в хранилище, код не правится) + одинаковые проверки для каждого бота.
- **Паспорт бота.** Все паспорта лежат в KV одним ключом `cfg:all` (`{ <id>: cfg }`). `compileClient(cfg)` превращает паспорт в объект клиента (как в `CLIENTS`): разбирает график (`parseSchedule`), услуги (`parseServices`), мастеров, берёт тексты ниши из `NICHES`. `syncClients(env)` подгружает паспорта в начале каждого запроса (не чаще раза в минуту на экземпляр). Паспорт с ошибками в бота не превращается. Встроенные демо (`BUILTIN`) паспортом не заменяются.
- **Секреты клиента — только в Cloudflare**, по имени: `WA_TOKEN_<ID>`, `APP_SECRET_<ID>`, `PHONE_NUMBER_ID_<ID>` (или поле паспорта `waPhoneId`), `TG_CHAT_<ID>` (или `tg` в паспорте), `KEY_<ID>`, `ALTEGIO_LOC_<ID>`. В паспорт и в репозиторий секреты не попадают.
- **Вход.** Ключ вводится один раз → cookie `aia` на 30 дней (HttpOnly, Secure, SameSite=Lax; подпись HMAC от `LEADS_KEY`). Владелец входит ключом `LEADS_KEY`; сотрудник клиента — своим ключом (в паспорте хранится только его хеш `keyHash`; смена ключа гасит старые сессии). Сотрудник видит только своего клиента (`canSee`). Все изменяющие запросы проверяют источник (`sameOrigin`). Страницы отдаются через `page()` (без кэша, без встраивания).
- **Страницы:** `/studio` — «Мои боты» (только владелец): форма паспорта, проверка, ключ сотрудника. `/launch?c=<id>` — проверка запуска: чек-лист подключений и экзамен бота на живой модели (сценарии собираются из паспорта, `casesFor`). `/inbox?c=<id>` — пульт чатов. `/broadcast?c=<id>` — рассылки. `/leads` открывается и по cookie.
- **WhatsApp на несколько клиентов:** вебхук `/wa/<id>`. Подпись Meta обязательна (`APP_SECRET_<ID>`), ответ уходит токеном `WA_TOKEN_<ID>` с того номера, на который написали (`metadata.phone_number_id`). Прежний режим (один номер на воркер: `POST /`, `WA_TOKEN`, `WA_CLIENT`) работает как раньше. Вебхук обрабатывает все сообщения пачки (`WA_BATCH`), остальные кладёт в пульт с пометкой.
- **История чата** — один ключ `h:<канал>:<клиент>:<id>`: `{ n, turns: [{ role, text, t, by?, m? }], profile }`. Хранится `HIST_KEEP` (60) реплик, в ИИ уходит `MAX_TURNS` (24). Метаданные ключа (`histMeta`) — это строка списка чатов в пульте: список читается одним `KV.list` без чтения чатов. Писать историю только через `putHist`/`logTurns`.
- **Пульт чатов.** `profile.need = { at, why }` поднимает чат в «Ждут ответа» (`human`, `limit`, `media`, `ai`, `req`, `lead`, `call`, `off`). Ответ администратора (`by: "admin"`) ставит бота в этом чате на паузу на 2 часа; есть «Вернуть бота», «Остановить на 12 часов», «Сделано → сообщить клиенту» для просьб об отмене и переносе (заявка получает статус «выполнена», запись убирается из `profile.bookings`). Писать клиенту можно только в 24-часовом окне WhatsApp (`profile.li`). В чат на сайте ответить нельзя.
- **Рассылки** (раздел «РАССЫЛКИ» в конце `worker.js`). Только шаблоны, одобренные Meta. Отправляет фоновая задача: `scheduled` → `cronRun` раз в минуту (cron в `wrangler.jsonc`; у черновиков cron не работает — на странице есть кнопка «Отправить порцию сейчас»). Правила: порция отмечается отправленной **до** отправки (никто не получает сообщение дважды; оборванная порция помечается «неизвестно»); тем, кто в списке `optout:<клиент>:<номер>`, не шлём («стоп» боту, отказ от рекламы в WhatsApp, кнопка «Остановить рекламу»); предел на скользящие 24 часа общий для клиента (`bcq`); часы отправки 8–22. Ошибки Meta: `BC_TEMP` — ждать 10 минут, `BC_ACCOUNT` — пауза и получатель обратно в очередь, `BC_PARAM` — пауза, со второго раза получатель пропускается, пять ошибок подряд — пауза. Сигналы Meta с вебхука (`waSignal`: шаблон приостановлен, качество упало, аккаунт ограничен) ставят рассылки на паузу (`bchold`). Текст последней рассылки (`bclast`) 7 дней виден ИИ в чатах WhatsApp и администратору в пульте. Меняешь эту часть — сначала сценарий в `test/platform.mjs`.
- **KV пишет один ключ не чаще раза в секунду** (иначе отказ 429). Любая запись «прочитал → изменил → записал» в ключ, который могут писать два запроса подряд, идёт через `kvRetry`. Проверить новое место: `KV_STRICT=1 node test/platform.mjs` (строгий KV; из-за секундных пауз часть сценариев в нём не проходит — смотреть нужно на необработанные отказы).
- **Проверки платформы:** `test/harness.mjs` — обвязка (KV в памяти с метаданными, заглушки Gemini, Telegram, Meta, Altegio; `mk()` → сайт с помощниками, `S.cron()` — фоновая задача). `test/platform.mjs` — проверки новых частей (запускается из `test/smoke.mjs`). `test/devserver.mjs` — локальный сервер на заглушках (`node test/devserver.mjs`, вход ключом `owner-key-123456`). `test/e2e.mjs` — сценарий в настоящем браузере (Playwright, в `npm test` не входит): `node test/e2e.mjs <папка для снимков>`.
- **Известные ограничения:** гонки KV (два сообщения одного чата одновременно; две страницы владельца, сохраняющие разные паспорта; фоновая и ручная отправка рассылки в одну и ту же секунду) — полностью закрываются только Durable Object; бесплатный тариф Cloudflare (1000 записей и 1000 списков KV в сутки, 10 мс процессора) для настоящего клиента с WhatsApp мал — перед запуском нужен платный ($5).

## Altegio
- Используется публичный API онлайн-записи (`api.alteg.io/api/v1/book_*`): нужен только ключ разработчика (секрет `ALTEGIO_PARTNER` в Cloudflare) и номер локации клиента. Справочник: developer.alteg.io/en/public/openapi/online-booking.
- Справочнику верь не до конца, проверяй вживую. Проверено на настоящем Altegio (3 октября 2026, пробная локация): чтение услуг, мастеров, дат и времени; `book_check`; создание записи и её удаление. Создание без поля `email` отвечает 422, хотя в справочнике поле необязательное, — бот передаёт его пустым (`altRecord`). Номер с «+» принимается. Длительность услуги (`seance_length`) в `book_services` без мастера не приходит.
- Локация клиента: `altegio.location` в его блоке `CLIENTS` или переменная `ALTEGIO_LOC_<ID>`. Тестовый клиент `alt` скрыт с витрины.
- **Два режима отмены и переноса** (`altSelfCancel`). По умолчанию — **режим администратора**: бот в расписании ничего не удаляет; просьбу клиента об отмене или переносе он передаёт администратору заявкой (`kind: "cancel"` или `"change"`, видна на `/leads`) и сообщением в Telegram, клиенту отвечает «передала администратору» (`cxAdmin`, `mvAdmin`). Так запускаем первого заказчика. Второй режим — бот отменяет и переносит сам: Text `ALTEGIO_SELF_CANCEL` = `1` (или `ALTEGIO_SELF_CANCEL_<ID>`, или `altegio.selfCancel` в блоке клиента). Не включать, пока не сделано правило «перед любой отменой бот переспрашивает» и не пройдена ещё одна независимая проверка.
- Режим администратора: просьба уходит, когда об отмене или переносе просил сам клиент (`wantsChange`) и ИИ это подтвердил — строкой `[ОТМЕНА]`, словами «отменила» или «передала администратору» (`ADMIN_CX`). ИИ поставил `[ОТМЕНА]` без просьбы клиента — ничего не происходит. Пара строк `[ОТМЕНА]` + `[ЗАЯВКА]` на уже записанного человека — просьба о переносе (новую запись бот не создаёт), кроме случая, когда клиент сказал «ещё». Запись, которой нет в чате, — тоже заявка (с телефоном). Клиент передумал или снова записывается на то же время — администратору «клиент передумал». Одна просьба — одна заявка (`profile.req`), записи с просьбой помечены `rq`.
- Клиент передумал («не надо отменять», «оставьте запись») — администратору уходит «клиент передумал», а заявка-просьба на `/leads` получает статус «клиент передумал». Клиент снова записывается на то же время — бот напоминает о просьбе и подсказывает написать «оставьте запись» (сам ничего не решает).
- Частица «не» в правилах просьб (`ALT_WANT_CHANGE`, `ALT_KEEP`, `ALT_UNDO`, `MOVE_WISH`) — только отдельным словом (`(?<![а-яё])не`). Без этого «мне нужно отменить запись» читалось как «не нужно отменять». Добавляешь правило с «не» — ставь эту границу и пример в тесты.
- Всё, что ниже про отмену и перенос самим ботом (`samePerson`, `cxAsk`, «да» отменяет), относится к режиму `ALTEGIO_SELF_CANCEL`. Старые проверки (`test/smoke.mjs` до раздела «режим по умолчанию», `test/review/`) идут в этом режиме.
- Итог записи, отмены и переноса клиенту сообщает код (`altSay`) по ответу Altegio, а не текст ИИ. ИИ только ставит служебные строки `[ЗАЯВКА]` и `[ОТМЕНА]`. Фразы ИИ «записала / отменила / перенесла» без служебной строки до клиента не доходят (`altClaims`). Если после изменений фильтр начал портить обычные ответы или пропускать ложные — правь списки `CLAIM_*` и `CL_*` и добавляй пример в тесты.
- Активные записи чата — в `profile.bookings`, заявки, которые ждут администратора, — в `profile.pend`. Перенос = `[ОТМЕНА]` + `[ЗАЯВКА]` в одном ответе: сначала создаётся новая запись, потом удаляется старая.
- Отмена удаляет только запись из этого чата, названную в строке отмены. Имена сравниваются строго (`samePerson`): «Жанар» ≠ «Жанат», «Тимур Ахметов» ≠ «Тимур Иванов»; латиница и казахские буквы приводятся к русским («Timur» = «Тимур», «Айгүл» = «Айгуль»).
- Бот не удаляет запись молча, если есть сомнение: строка `[ОТМЕНА]` без подробностей, а клиент назвал другое имя, день или время; имя в строке не совпало; строка была в ответе, который отклонила защита. Тогда бот спрашивает «Отменить запись …?» и запоминает вопрос (`profile.cxAsk`); ответ «да» отменяет именно эту запись, что бы ни написал ИИ.
- Телефон берётся только у клиента (из его сообщения или номера WhatsApp), а не из строки ИИ.
- Названия услуг и имена мастеров из Altegio очищаются (`altText`): знаки `; | [ ] { } :` ломают разбор служебных строк. Услуга и мастер подбираются так: не уверены — переспрашиваем, а не угадываем (`altPickServices` → `{list}` или `{ask}`, `altPickStaff` → `{staff}`, `{any}` или `{ask}`). «Не Арман» и «любой, кроме Армана» — это не «любой».
- Поля служебных строк (`tagFields`) читаются и с ключами на английском и казахском, с разными разделителями; дата — в нескольких видах (`altDateOf`).
- Если Altegio не принял запись или недоступен, бот не теряет клиента: создаёт заявку администратору с пометкой. Если свободного времени нет совсем — заявку на обратный звонок (не чаще раза в час на чат; в браузер от неё уходит только телефон). Заявок администратору из одного чата — не больше 6 в сутки.
- Лимиты автоматических записей: 4 на чат, 5 в сутки на телефон, 15 в сутки на IP, 60 в сутки на локацию; сверх лимита — заявка администратору. Перенос записи лимиты не тратит.
- WhatsApp без подписи Meta (`APP_SECRET` не задан): бот сам в расписание не записывает.
- Заявки, история чата и уведомления сохраняются в конце сообщения в таком порядке: заявки → история → ответ клиенту → Telegram (`opts.defer`). Сбой хранилища не должен ронять ответ клиенту.
- Заявка хранится дважды: в общем списке `leads:<клиент>` и отдельным ключом `lead:<клиент>:<день>:<id>` (`leadKey`). Общий список может потерять заявку, когда два чата пишут его одновременно; страница `/leads` возвращает такие заявки из отдельных ключей за последние 7 дней (`allLeads`).
- Страховка от ошибок в коде: разбор ответа ИИ обёрнут в `try` (клиент получает «передала администратору», администратор — сигнал), вокруг всего `think()` — `thinkSafe`.
- Два сообщения одного чата одновременно: при сохранении история сливается (`mergeProfile`). Полной защиты от гонки нет — для неё нужен Durable Object.
- `/altegio?key=<LEADS_KEY>[&loc=<номер>]` — что бот видит в Altegio. Кнопка «Пробная запись» создаёт запись и сразу удаляет её.
- Вживую с настоящим Altegio проверяй после каждого изменения этой части: страница `/altegio` и чат `/?c=alt`. Страница `/altegio` показывает и режим отмены, и настроен ли Telegram.
- Без Telegram (`TG_TOKEN`, `TG_CHAT`) запускать клиента нельзя: в режиме администратора отмены и переносы приходят именно туда (без него они видны только на `/leads`).

## Правила
- Ветка `main` = боевой сайт: Cloudflare Workers Builds выкладывает каждый коммит в `main` (сначала `node test/smoke.mjs`, потом `npx wrangler deploy`).
- Любая ветка, кроме `main`, = черновик: Cloudflare собирает для неё отдельный адрес (`npx wrangler preview`, Worker Previews), рабочий сайт не меняется. Новое делай в `dev`.
- Для черновиков в `wrangler.jsonc` обязателен блок `previews` (без него сборка падает). Черновик не наследует настройки рабочего сайта: хранилище KV прописано в `previews` (то же, что у рабочего сайта), переменные и секреты — в панели: Settings → Previews. Новый секрет в панели получают только новые черновики (новая ветка).
- Адрес черновика ветки `dev` по документации Cloudflare: `https://dev-ai-admin.azikonps4.workers.dev`.
- Перед `main`: `npm test` (на Node 20 и 22) и сравнение со старой версией для клиентов без Altegio. После выкладки — живой автотест: `/api/selftest?key=<LEADS_KEY>&i=<номер>`.
- Результат сборки виден без панели: `gh api repos/aztenel/ai-admin/commits/<sha>/check-runs`.
